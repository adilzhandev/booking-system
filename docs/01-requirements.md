# Этап 1 — Requirements

Статус: требования описаны; реализация API ещё не начата.

## Что и зачем делаем

Определяем поведение системы до написания классов. Требования должны позволять
ответить: «Какой запрос допустим? Кто имеет доступ? Как проверить результат?»
Все уточнения ниже — исходные проектные решения MVP; их можно обсудить с mentor.

## Границы проекта

REST API бронирования переговорных одного офиса. Один Spring Boot процесс,
одна PostgreSQL БД, один Maven-модуль. Логические модули: пользователи и доступ,
комнаты, бронирования. Это небольшой modular monolith с пакетами по слоям;
границы модулей пока поддерживаются структурой кода, без отдельных сборок.

В MVP нет UI, оплаты, повторяющихся встреч, приглашений, уведомлений, refresh
токенов, восстановления пароля, редактирования времени существующей брони.
Для изменения времени пользователь отменяет бронь и создаёт новую; это две
операции, поэтому свободное время между ними не резервируется.

## Функциональные требования

| ID | Требование | Проверяемый результат |
|---|---|---|
| F01 | Регистрация по email, паролю, имени и фамилии | Создан USER; пароль в БД — BCrypt hash; ответ без пароля/hash |
| F02 | Email уникален без учёта регистра | ` User@Example.com ` нормализуется; повторная регистрация → 409 |
| F03 | Авторизация | Верные данные → JWT; неверные → 401 с общим сообщением |
| F04 | Каталог и карточка комнаты | Авторизованный пользователь видит активные комнаты |
| F05 | Проверка доступности заданного интервала | Возвращает available; ответ не резервирует комнату |
| F06 | Создание брони | Владелец берётся из principal; успешный запрос → 201 |
| F07 | Просмотр своих броней | Страница содержит только записи текущего пользователя, включая CANCELLED |
| F08 | Просмотр отдельной брони | Владелец или ADMIN → 200; чужая для USER → 403 |
| F09 | Отмена своей брони | ACTIVE → CANCELLED; запись остаётся в БД; ответ 204 |
| F10 | Управление комнатами | Только ADMIN создаёт, изменяет, деактивирует комнаты |
| F11 | Просмотр всех броней | Только ADMIN, с pagination и sorting |
| F12 | Защита от конкуренции | Две конкурирующие валидные заявки на один интервал: одна 201, другая 409 |

ADMIN получает возможности USER и административные возможности. ADMIN видит
любую бронь, но отменяет через `/api/bookings/{id}` только собственную.
Регистрация не принимает role, id или createdAt. Первый ADMIN назначается
отдельной локальной операцией после регистрации; публичного API повышения роли
и пароля администратора в миграциях не будет.

## User stories и acceptance criteria

1. **Как сотрудник, я хочу зарегистрироваться и войти**, чтобы бронировать комнаты.
   При валидной регистрации получаю 201 с профилем; затем login возвращает 200
   с accessToken, tokenType=Bearer и expiresIn. Email-дубликат даёт 409.
2. **Как сотрудник, я хочу найти комнату**, чтобы выбрать подходящую вместимость.
   Каталог возвращает только active=true, поддерживает страницы и сортировку.
   Несуществующая или неактивная карточка комнаты возвращает 404.
3. **Как сотрудник, я хочу проверить время**, чтобы спланировать встречу.
   Для [10:00, 11:00) с активной бронью [10:30, 11:30) получаю available=false;
   для соседней брони [11:00, 12:00) — true.
4. **Как сотрудник, я хочу создать бронь**, чтобы закрепить комнату за встречей.
   Для свободной активной комнаты и будущего валидного интервала получаю 201;
   при пересечении — 409. Подмена userId в запросе недопустима.
5. **Как владелец, я хочу отменить бронь**, чтобы освободить время.
   После отмены интервал можно забронировать; повторная отмена своей брони → 204.
   Чужая бронь → 403, отсутствующая → 404.
6. **Как администратор, я хочу отключить комнату**, чтобы запретить новые брони.
   DELETE меняет active на false; история и существующие брони сохраняются.
   Повторная деактивация → 204; неизвестный id → 404.
7. **Как администратор, я хочу видеть все брони**, чтобы контролировать расписание.
   ADMIN получает страницу всех статусов, USER получает 403.
8. **Как сотрудник, я хочу надёжное подтверждение брони**, даже при одновременных запросах.
   Для двух разных сотрудников и одинакового слота сохраняется одна ACTIVE
   запись. Проверяем это на PostgreSQL с двумя отдельными транзакциями.

## Бизнес-правила

- Время в API — ISO 8601 с offset, например `2030-01-10T10:00:00+05:00`.
  В Java планируем Instant, в PostgreSQL — timestamptz; ответы времени — UTC (`Z`).
- Интервал полуоткрытый: `[startTime, endTime)`. Встречи могут идти подряд.
- `startTime` строго позже текущего времени сервера; `endTime > startTime`.
  DTO получит @NotNull и @Future; сервис проверяет диапазон и текущее время
  через внедрённый Clock после получения блокировки комнаты.
- Пересечение: `existing.startTime < new.endTime AND existing.endTime > new.startTime`.
  Учитываются только ACTIVE записи той же комнаты.
- CANCELLED не занимает время. ACTIVE означает «не отменена», а не «идёт сейчас»;
  прошедшие встречи автоматически не меняют статус.
- Время, room и user существующей брони неизменяемы через API.
- Создание в inactive комнате → 409; отсутствующий roomId → 404.
- Проверка availability для inactive или отсутствующей комнаты → 404;
  неправильный/прошедший интервал → 400. Ответ — снимок, не гарантия будущего POST.
- Деактивация запрещает новые брони, но не отменяет существующие.
  Создание и деактивация используют блокировку одной строки Room:
  если деактивация завершилась первой, последующий создатель получает 409;
  если создание первым захватило блокировку, его бронь сохраняется.
- Отмена своей уже прошедшей брони разрешена для простоты MVP; это изменение
  статуса в истории, а не физическое удаление. Более строгая политика — отдельно.
- Ограничения рабочих часов, длительности и параллельных броней пользователя
  в разных комнатах не вводим. Вместимость положительна; участников пока нет.
- Имя комнаты не уникально: технический идентификатор — id.

## Контракт API

Все маршруты кроме auth и документации требуют Bearer JWT.

| Метод | Путь | Доступ | Успех |
|---|---|---|---|
| POST | /api/auth/register | Публичный | 201, профиль без password |
| POST | /api/auth/login | Публичный | 200, JWT |
| GET | /api/rooms | USER, ADMIN | 200, страница активных комнат |
| GET | /api/rooms/{id} | USER, ADMIN | 200, комната |
| GET | /api/rooms/{id}/availability?startTime=…&endTime=… | USER, ADMIN | 200, roomId/startTime/endTime/available |
| POST | /api/admin/rooms | ADMIN | 201, комната |
| PUT | /api/admin/rooms/{id} | ADMIN | 200, обновлённая комната |
| DELETE | /api/admin/rooms/{id} | ADMIN | 204, деактивация |
| POST | /api/bookings | USER, ADMIN | 201, бронь |
| GET | /api/bookings/my | USER, ADMIN | 200, страница своих броней |
| GET | /api/bookings/{id} | Владелец, ADMIN | 200, бронь |
| DELETE | /api/bookings/{id} | Только владелец | 204, отмена |
| GET | /api/admin/bookings | ADMIN | 200, страница всех броней |

POST Room: name, capacity, description; active=true выставляет сервер.
PUT Room: полное обновление name, capacity, description, active;
active=true также позволяет вернуть отключённую комнату в каталог.
POST Booking: только roomId, startTime, endTime; status=ACTIVE и user берёт сервер.
Поля вне схемы входного DTO отклоняем с 400, чтобы role/userId нельзя было
незаметно проигнорировать и принять за поддерживаемые параметры.

Pagination: page ≥ 0, 1 ≤ size ≤ 100, defaults page=0 и size=10.
Rooms: разрешены sort=id/name/capacity/createdAt, default name,asc.
Bookings: sort=id/startTime/endTime/createdAt, default startTime,desc.
Направления asc/desc; неизвестные поля и некорректные параметры → 400.
К сортировке добавляем id как tie-breaker. Ответ — отдельный PageResponse DTO:
content, page, size, totalElements, totalPages. Динамические изменения данных
могут сдвигать offset-страницы; для MVP это приемлемо.

## Валидация и ошибки

- Email: @NotBlank, @Email, @Size(max=254), trim и lowercase(Locale.ROOT).
- Пароль: @NotBlank, @Size(min=8, max=72) плюс проверка длины UTF-8 ≤ 72 байта
  для BCrypt. Не trim-ить пароль, не логировать; Unicode символы могут занимать
  несколько байтов, поэтому одной @Size недостаточно.
- Имя, фамилия и room.name: @NotBlank, @Size(max=100).
- capacity: @NotNull, @Positive; description: @Size(max=2000), допускает null.
- roomId: @NotNull, @Positive; время: @NotNull, startTime: @Future;
  сравнение двух времён выполняется отдельно в сервисе.

| HTTP | Когда |
|---|---|
| 400 | Невалидный JSON, поля, pagination, время |
| 401 | Нет/невалиден/истёк JWT, неверные login credentials |
| 403 | Недостаточно прав, попытка отменить чужую бронь |
| 404 | Ресурс не найден; inactive Room скрыта в пользовательском GET |
| 409 | Email занят, комната inactive при создании, пересечение брони |
| 500 | Неожиданная ошибка без раскрытия SQL, stack trace и секретов |

```json
{
  "timestamp": "2030-01-10T05:20:30Z",
  "status": 409,
  "error": "Conflict",
  "message": "Комната уже забронирована на выбранное время",
  "path": "/api/bookings"
}
```

@RestControllerAdvice обрабатывает ошибки MVC/сервисов. Ошибки security filter
chain требуют AuthenticationEntryPoint и AccessDeniedHandler с тем же JSON:
один Advice не покрывает ошибки, возникшие до Controller.

## Нефункциональные требования

- **Целостность:** ни при конкуренции, ни при обходе Java-кода БД не допускает
  пересекающиеся ACTIVE брони одной комнаты. FK/NOT NULL/CHECK защищают структуру.
- **Безопасность:** BCrypt; JWT с проверкой подписи и срока; stateless filter
  chain; сервер назначает роль и владельца. Секреты из окружения, не из Git.
  Целевой TTL access token — 30 минут; logout/досрочный отзыв пока вне MVP.
- **Поддерживаемость:** Controllers тонкие, транзакции/правила в Service,
  Repository для БД, DTO отдельно от Entity. Ручной mapper для трёх сущностей;
  MapStruct добавим только если повторение кода станет заметным.
- **Предсказуемость:** единый формат ошибок, явная временная зона, стабильная
  дополнительная сортировка, ограниченный размер страниц.
- **Доступ к данным:** индексы по реальным запросам; избегаем N+1; планируем
  open-in-view=false. Не обещаем конкретный RPS/latency без нагрузочного теста.
- **Воспроизводимость:** Maven Wrapper, Java 21; схема только через Flyway;
  Hibernate ddl-auto=validate, не update. Docker Compose запускает backend+DB.
- **Аудит:** createdAt неизменяемый, назначается сервером через JPA auditing;
  DEFAULT current_timestamp в БД служит fallback для SQL-вставок.
- **Тестируемость:** JUnit 5/Mockito для правил, Testcontainers PostgreSQL для
  миграций/API/гонок, управляемый Clock. H2 не заменяет PostgreSQL в этих тестах.
- **Документация:** README честно отражает реализованные возможности;
  OpenAPI описывает DTO, Bearer auth, ошибки и pagination.

## Критерии готовности всего проекта

1. `docker compose up --build` поднимает API и PostgreSQL после настройки окружения.
2. Swagger открывается в браузере; register → login → create booking работает.
3. Все бизнес-правила выше покрыты подходящими тестами.
4. Unit tests BookingService: успех, занятая комната, неверный диапазон,
   inactive комната, чужая отмена, своя отмена; дополнительно прошлое время.
5. Testcontainers проверяет API создания и две реальные конкурирующие заявки:
   статусы 201/409 и ровно одна ACTIVE запись; соседние интервалы разрешены.
6. Нет Entity/password/hash в REST-ответах и секретов в репозитории.

## Типичные ошибки Junior

- Начать с Entity и обнаружить неоднозначные правила при написании тестов.
- Перепутать 401 и 403, возвращать 200 для любого результата.
- Доверять userId/role из JSON или считать availability обещанием брони.
- Не определить границы интервала и часовой пояс.
- Считать `@Transactional` или `if (exists)` достаточной защитой от гонки.
